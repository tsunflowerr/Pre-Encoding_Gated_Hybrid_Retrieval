### 2. [P2] Utility CLI ghép được hai run khác split/fold và thiếu query

Vị trí: `scripts_a/build_utility.py:26–32`.

Script chỉ so sánh corpus hash, rồi evaluate cả hai run trên query file đầy đủ.
Missing rankings trở thành 0 trước khi join, nên việc so sánh query sets trong
`utility_rows` không phát hiện được query vốn không có trong input run.

Đã đưa baseline `train/fold=0` và candidate `test/fold=1` có hai query sets khác
nhau vào CLI. Script exit 0 và xuất utility cho cả năm fixture queries, gồm hai
delta `+1` và `-1` do query vắng ở một bên. Dùng output này làm nhãn gate có thể
gán gain sai hoặc đưa sai split vào dữ liệu huấn luyện.

Đề nghị: yêu cầu cả hai run có đúng query set dự kiến; cho phép explicit empty
ranking nhưng không biến record bị thiếu thành nhãn hợp lệ. Kiểm split/fold và
binding dữ liệu trước khi tính utility; method/run ID của baseline và candidate
có thể khác nhau theo thiết kế. Lưu input hashes và provenance của utility.

Quy tắc missing query = 0 vẫn phù hợp cho báo cáo evaluation độ bao phủ; bước
tạo nhãn huấn luyện cần validation chặt hơn trước khi gọi evaluator.

### 3. [P2] Sparse loader chưa xác minh hash của manifest chi phối score

Vị trí: `src/pegh/sparse/index.py:129–138`; hash được tạo ở 119 nhưng chưa kiểm
lại khi load.

Loader kiểm bytes SQLite và tokenizer/config fingerprint. Các field như
`average_document_length`, `corpus_sha256`, `document_count` nằm ngoài kiểm tra
đó, dù ảnh hưởng score hoặc danh tính artifact.

Đã sửa riêng `average_document_length *= 10` trong bản sao manifest fixture.
Loader vẫn chấp nhận; score top-1 đổi từ `7.398496895488511` thành
`12.115073659986209` nhưng `retriever_hash` giữ nguyên. Như vậy hash không còn
đại diện đúng cho hệ thống đang chạy khi metadata bị sai.

Đề nghị: recompute `object_hash` của manifest bỏ field `retriever_hash`, đối chiếu
trước load; kiểm status/schema, các statistics hữu hạn/hợp lệ và count/length với
SQLite khi cần. Thêm test thay riêng average length/corpus hash mà giữ nguyên DB.
